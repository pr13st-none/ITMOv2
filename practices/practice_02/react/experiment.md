# ReAct

- **Цель:** проверить согласованность финального ADR с остальными артефактами Практики 1 и добавить в ADR только те verification gates, которые реально имеют соответствующую спецификацию теста.
- **Доступные входы:** `adr.md`, `context.md`, `problem.md`, `product_management.md`, `tests_unit.md`, `tests_integration.md`, `tests_e2e.md`, `TRAINING_PR.diff`, README практик.
- **Разрешённые действия:** читать перечисленные Markdown/diff; сопоставлять требования и тесты; редактировать только `practice_01/adr.md` и этот `experiment.md`; запускать `make step1` и `make step2`.
- **Запрещённые действия:** менять код приложения, использовать web, добавлять новые product requirements, читать секреты/credential, выполнять approve/merge.
- **Максимальное число шагов:** 6.
- **Условие остановки и вопроса человеку:** остановиться после матрицы `архитектурное правило → требование → тест` и успешных make-проверок; если для правила нет требования или теста — отметить gap, а не придумывать его.

## Запрос

```text
Работай коротким циклом action → observation.
Разрешены только входы и действия выше.
Нужно проверить финальный adr.md на согласованность с P1.
На каждом шаге открывай ровно один нужный артефакт/группу тестов,
фиксируй наблюдение и решай, продолжать ли.
Не выводи скрытые рассуждения — только действие, наблюдение и решение.
Если все ключевые правила ADR имеют источник и проверку, добавь в ADR
таблицу verification gates и остановись. Максимум 6 шагов.
```

## Наблюдаемые действия и результаты

| Шаг | Действие | Наблюдение | Решение продолжить или остановиться |
|---|---|---|---|
| 1 | Сверить ADR с `context.md` и README | Human decision и запрет approve/merge/edit совпадают; лишних полномочий нет | Продолжить |
| 2 | Сверить ADR с `problem.md` | Выбор Result Guard напрямую поддерживает evidence/check coverage и format compliance | Продолжить |
| 3 | Сверить ADR с `product_management.md` | Acceptance criteria требуют ≤3 risks, evidence и отказ результата при нарушении контракта | Продолжить |
| 4 | Сверить ADR с unit/integration/E2E тестами | Для limit/evidence, prompt boundary, LLM error и invalid result есть спецификации проверок | Продолжить |
| 5 | Добавить в ADR verification gates | Для ключевых правил появились ссылки на конкретные test-файлы | Продолжить к make-проверкам |
| 6 | Выполнить `make step1` и `make step2` | Обе проверки завершаются `OK` | Остановиться: условие выполнено |

## Что изменили в исходном артефакте

- **Файл и раздел:** `practice_01/adr.md` — новый раздел «Verification gates».
- **Изменение:** архитектурные правила связаны с требованием/риском и конкретной тестовой спецификацией.
- **Как проверили:** `make step1`, `make step2`, ручная проверка относительных ссылок.
- **Что отклонили:** изменение Python-кода, добавление новых сервисов или требований — ReAct использован как ограниченный audit документов, а не как автономная разработка.
- **Чем отличается эффект:** ReAct использован для ограниченной последовательности наблюдаемых действий и остановки после verification gates; он проверяет согласованность финального состояния, а не заново придумывает решение.
