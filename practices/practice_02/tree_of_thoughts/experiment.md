# Tree of Thoughts

- **Решение, для которого нужны альтернативы:** как организовать первый сценарий AI-review одного diff так, чтобы сохранить смысловой анализ LLM, но сделать результат проверяемым и не расширять полномочия без необходимости.
- **Критерии выбора:** доказательность, минимальные полномочия, автоматическая проверяемость, соответствие scope одного diff, сложность первого инкремента.

## Запрос

```text
Сформируй ровно три архитектурных варианта для первого use case:
A — минимальный raw-prompt подход,
B — bounded pipeline с Context Pack и result validation,
C — автономный tool-using agent с доступом к репозиторию.
Сравни варианты только по пяти критериям из adr.md.
Не добавляй критерии стоимости/масштабирования, которых нет в задаче.
Выбери вариант, который лучше соответствует текущему use case, и назови его ограничения.
```

## Варианты решения

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A. Raw prompt + LLM | Минимальная реализация, уже близко к текущему diff | Нет обязательного evidence/формата; трудно валидировать; baseline показал лишние claims | Простота высокая; доказательность и проверяемость низкие |
| B. Bounded pipeline | Явный Context Pack, result guard, least privilege, хорошо маппится на тесты | Нужно добавить контракт и валидатор; модель остаётся недетерминированной | Лучший баланс всех пяти критериев для одного diff |
| C. Tool-using agent | Может собрать больше контекста и выполнять глубокие проверки | Выходит за scope, увеличивает права и число входов, сложнее воспроизводить | Потенциальная глубина высокая, но least privilege/scope/простота хуже |

## Выбор

- **Выбранная альтернатива:** B — bounded pipeline.
- **Почему:** это единственный вариант, который сохраняет смысловой LLM-review и одновременно делает evidence/формат частью проверяемого контракта без выдачи модели лишних инструментов.
- **Как проверим:** acceptance criteria из `product_management.md` + unit/integration/E2E проверки; для каждого архитектурного правила должна существовать проверка.

## Что изменили в исходном артефакте

- **Файл и раздел:** `practice_01/adr.md` — «Рассмотренные альтернативы» и «Решение».
- **Изменение:** альтернативы сведены в одну сравнимую матрицу по тем же критериям, явно зафиксирован выбор B и его ограничения.
- **Что отклонили:** A — не решает проблему evidence; C — избыточен для первого сценария и нарушает least privilege.
- **Как проверили:** все три варианта сравнены по одному набору критериев из ADR; выбранный B не требует источников или полномочий вне первого use case; `make step1` проходит.
- **Чем отличается эффект:** ToT дал явное сравнение альтернатив и причину выбора, тогда как остальные техники уточняют контракт уже выбранного решения.
