# Рефлексия

Больше всего пользы дало сочетание `AGENTS.md` и автоматической проверки после изменения. Правила снимают повторяющиеся уточнения из промпта, а hook сразу дописывает результат `python check.py` в ответ инструмента, поэтому агент видит `FAIL` или `PASS` в той же сессии.

TDD skill оказался полезен как ограничение порядка действий. На diff с NUL-байтом тест сначала упал с `DID NOT RAISE`, после изменения валидатора hook показал `8 passed`. Агент сначала вставил проверку не туда: тест снова упал, и только следующая правка дала green. После этого я убрал дублирование проверки, не меняя тест.

MCP я специально сделал маленьким и read-only: он проверяет payload перед code review и использует ту же `check_payload`, что и обычный код. На корректном входе возвращается размер diff, на пустом — контролируемая ошибка `diff_required`. Так не появляется второй набор правил, который потом пришлось бы синхронизировать вручную.

Ручное вмешательство потребовалось при настройке локальной модели: контекст 4096 не вмещал правила, tool-схемы и MCP, поэтому я увеличил `num_ctx` до 16384. Ещё пришлось заменить запуск через Windows `.cmd` на прямой вызов `opencode.exe`: многострочный промпт с кодом доходил некорректно. До исправления получались ошибки импорта в тесте, а не падение из-за отсутствующей проверки; такой запуск я не считал успешным red. Даже после исправления маленькая модель путала пути, поэтому полезнее смотреть на события инструментов и runner, чем доверять её слову «готово».

Ограничение осталось содержательным: hook подтверждает, что тесты проходят, но не доказывает, что тест проверяет правильное требование. Формулировку наблюдаемого поведения и полезность MCP tool всё равно должен оценивать человек.
