# Нагрузочные проверки

Для первого учебного сценария **нет подтверждённых требований по RPS, размеру diff, latency или quota провайдера**. Поэтому сейчас нельзя честно задать production SLO. Нагрузочный этап используется как characterization: получить baseline собственного API с fake LLM и отдельно измерить вклад реальной модели. Числа нагрузки ниже — профиль эксперимента, а не требования продукта.

| Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Подтверждение |
|---|---|---|---|---|
| Steady API + Guard с мгновенным fake LLM | Эксперимент: 20 RPS, 60 секунд | Нет process crash / необработанных исключений; latency SLO пока не задаём, сохраняем p50/p95 как baseline | p50/p95, CPU, 5xx, число необработанных исключений | Нагрузочный отчёт на test/stage |
| Короткий burst с fake LLM | Эксперимент: 100 запросов за 5 секунд | После burst сервис остаётся доступен; запросы не должны обходить input/result validation | ошибки, p95, восстановление после burst | Нагрузочный отчёт |
| Реальная LLM | Эксперимент: 1 RPS, 5 минут или меньшая нагрузка в пределах выданной quota | Числовой latency/error SLO не задаём до замера провайдера; сохраняем фактические значения | end-to-end p50/p95, provider errors, quota/rate-limit ответы | Smoke/soak отчёт |

Performance acceptance threshold вводится только после появления трёх входов: ожидаемого профиля трафика, распределения размера diff и SLA/quota выбранного LLM-провайдера. До этого результаты этих сценариев — baseline для последующего решения, а не доказательство production-готовности.

## Как использовали AI

- Строка в [`prompts.md`](prompts.md): `P1-03`.
- Что проверил студент и какие исправления поручил агенту: числовые нагрузки оставлены только как воспроизводимые параметры эксперимента; они явно не названы SLA. Неизвестные performance-требования не подменяются выдуманными порогами.
