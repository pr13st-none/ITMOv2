## Context Pack для первого рабочего сценария

### Факты и правила

- Вход обоих экспериментов — один и тот же [`TRAINING_PR.diff`](TRAINING_PR.diff).
- Новый endpoint находится в `app/api.py`: `POST /api/reviews` принимает `payload: dict` и передаёт `payload["diff"]` в `review_service.review`.
- `ReviewService.review` находится в `app/review_service.py`: он формирует prompt из фиксированной инструкции и переданного diff, вызывает `LLM.generate` и возвращает поле `comment`.
- Для одного PR помощник должен вернуть: краткое описание изменения; **не больше трёх** рисков; список проверок.
- Для каждого риска обязательны файл/строка, evidence из доступного входа и воспроизводимая проверка.
- Если требование не дано в diff или правилах кейса, его нельзя выдавать за подтверждённый дефект. Его можно обозначить как неизвестное или возможное проектное решение.
- Решение о PR всегда принимает человек.

### Формат входа и результата

**Вход:** unified diff одного PR и этот Context Pack.

**Результат:**

1. краткое описание изменения;
2. от 0 до 3 рисков;
3. для каждого риска — `file:line`, наблюдаемое evidence, последствие и конкретная проверка;
4. короткий список проверок;
5. при необходимости — отдельный список неизвестных требований, которые нельзя подтвердить входом.

### Ограничения и запрещённые действия

- Не approve и не merge PR.
- Не изменять код.
- Не придумывать правила проекта, которых нет во входе.
- Не считать отсутствие опциональной best practice дефектом без подтверждённого требования.
- Не использовать web, историю рабочего чата или файлы вне разрешённого Context Pack в тестовом запуске.
- Не выводить скрытые рассуждения модели; нужен проверяемый итог и evidence.

### Хороший пример

> `app/api.py`, `create_review` — обращение `payload["diff"]` не проверяет наличие ключа. Проверка: отправить `POST /api/reviews` с `{}` и зафиксировать HTTP-ответ.

Хороший пример называет место, показывает наблюдаемый фрагмент и даёт проверку.

### Плохой пример

> Код можно улучшить. Добавьте валидацию, безопасность и тесты.

Плохой пример нельзя проверить: нет места, evidence и критерия, по которому утверждение можно принять или отклонить.

### Что пока неизвестно

- Требуются ли аутентификация, rate limit и квоты для endpoint.
- Допустимый максимальный размер diff и SLA полного запроса к LLM.
- Какой HTTP-контракт ошибок должен быть у production API.
- Должен ли production-ответ оставаться `{"comment": string}` или стать структурированным.
