# Проблема и метрики

## Проблема

- **Пользователь:** человек-ревьюер или разработчик, использующий AI как предварительный фильтр перед ручным review.
- **Ситуация:** для одного PR у помощника есть только diff; нужно быстро получить небольшой список реально проверяемых рисков.
- **Что происходит сейчас:** короткий запрос «посмотри PR и найди проблемы» не задаёт лимит, формат evidence, границы полномочий и правило для неизвестных требований. В baseline получился длинный список, где доказанные наблюдения смешаны с гипотезами.
- **Почему это мешает пользователю или бизнесу:** человек тратит время на проверку правдоподобных, но неподтверждённых замечаний и не может одинаково воспроизвести review на следующем PR.
- **Что не входит в задачу:** автоматический approve/merge, изменение кода, полный статический анализ репозитория, проверка требований, которых нет во входе.

## Метрики

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Evidence coverage | Доля рисков, где одновременно есть `file:line` и конкретный фрагмент/факт. В baseline — измеряется по `P1-01`. | 100% возвращённых рисков | После каждого тестового запуска | `results/P1-01.md`, `results/P1-02.md` |
| Check coverage | Доля рисков, для которых дана воспроизводимая проверка. | 100% возвращённых рисков | После каждого запуска | Результат review |
| Unsupported claims | Количество рисков, представленных как факт без подтверждения diff или правилом кейса. | 0 | После ручной сверки review с входом | `TRAINING_PR.diff`, `README.md` |
| Соблюдение формата | Есть summary, не более 3 рисков и список checks. | 100% запусков | На каждом запуске | Master Prompt v1 |

## Почему изменение метрики подтвердит решение проблемы

Проблема не в том, чтобы AI нашёл как можно больше замечаний, а в том, чтобы человек мог быстро проверить каждое из них. Поэтому 100% evidence и checks уменьшают ручной поиск контекста, ноль неподтверждённых claims убирает смешивание фактов с догадками, а лимит в три риска сохраняет результат обозримым. Эти показатели напрямую проверяют требования учебного кейса.

## Как использовали AI

- Для чего: сформулировать пользовательскую проблему так, чтобы она описывала качество AI-review, а не случайный набор возможных улучшений backend.
- Тип промпта: master prompting + проверка по источникам.
- Строка в [`prompts.md`](prompts.md): `P1-03`.
- Что проверил студент и какие исправления поручил агенту: метрики сделаны измеримыми по сохранённым результатам; убраны SLA/лимиты, которых нет во входных данных.
